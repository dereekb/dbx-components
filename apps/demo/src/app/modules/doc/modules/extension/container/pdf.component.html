Drop PDFs (application/pdf) and/or images (PNG/JPEG) into the upload area. Drag the handle on each row to reorder. Pages are appended in list order; image entries become a single page sized to the image.

Each slot owns its own upload area and inline file display, and is tagged with a `slotId`. The validator directive aggregates each slot's readiness — Preview/Download stay disabled until every required slot has a ready file. Optional slots (here, Insurance Card) only block when they contain an invalid file. State-aware icons projected through the slot's header use the `dbxPdfMergeEditorFileUploadHasState` directive.

Both slots here are single-file, so once one is filled it is at capacity and offers no Add — its header keeps only Clear , which is how a single-file slot's document gets replaced. Clearing confirms first through dbxActionConfirm .

Slot capacity defaults to `1` for single-file slots and to `maxFiles` when set. Both add affordances are gated on it: the `dbx-file-upload` drop area stands in while the slot is empty, the header `Add` button takes over once it owns something, and at capacity neither is offered — the user must remove an existing entry, or `Clear` the slot, before adding more.

A single [config] object (`DbxPdfMergeEditorConfig`) drives the whole editor: `imageCompression` to downscale and (optionally) convert images on upload, `outputSizeLimits` to surface warn/error banners, plus the display options (`fileName`, `showPreviewButton`, `showDownloadButton`, `showAddFiles`, `showFileList`, `accept`, `multiple`, `downloadButton`). Any individual input still overrides the matching config field. Crossing `errorBytes` blocks Preview/Download via the store's validity gate. Each compressed entry shows a "Resized" / "Converted PNG → JPEG" chip with the original byte count.

Wrap the trigger in [dbxPdfMergeEditorStore] and (optionally) a dbxAction with a handler. The dbxPdfMergeUploadButton directive registers a DbxButtonInterceptor on the host dbx-button — when the dialog returns a confirmed Blob it calls readyValue(blob) on the surrounding action source, and the sibling dbxActionButton directive handles the resulting click and pipes working/disabled state back to the button. Close the dialog without confirming to keep the editor entries for a later attempt.

The [dbxPdfMergeEditorStore] wrapper also accepts a [config] (`DbxPdfMergeEditorConfig`) — here `imageCompression` — that flows through the button into the dialog's default dbx-pdf-merge-editor , so large images are downscaled before the merge even though the dialog's editor has no inline config.

Pass a DbxPdfMergeUploadButtonConfig whose customDialogContent renders any custom dbx-pdf-merge-editor configuration (slots, multiple uploaders, etc.) and whose uploadButtonConfig overrides the dialog footer Upload button (text, icon, color, raised, flat/stroked/tonal/basic variant flags). Leave the inner component config's injector unset so the injected component inherits the dialog's injector and sees the same store.

With pageEditing enabled, each uploaded PDF expands into its individual pages. Pages can be reordered, rotated, and marked for deletion, and the Preview and Download buttons follow those edits live. Reordering is confined to a single slot — each group is its own drop list, so a page cannot be dragged from one document into another.

sidecar additionally embeds a JSON manifest and tags every output page, so a later reader can find a specific document's pages. Membership is recorded as page tags rather than positions: tags travel with their page through any subsequent reordering, while recorded indices would go stale. Each section header carries its own Add and Clear controls once the section owns something. Both sections here are multiple: true , so Add appends another document's pages to the same section rather than starting a new one; it hides only when the section reaches its maxFiles capacity. While the section is empty the full drop area stands in for the button, so there is never more than one add affordance on screen. Clear is a dbxAction wrapped in dbxActionConfirm — it prompts before emptying the section, since it discards that section's files and their page edits. Turn either control off with showAddButton / showClearButton , and override the prompt's copy (or skip it with autoConfirm ) through clearConfirm .

The same editor with pageEditing bound to a checkbox. Add a multi-page PDF and toggle it: off renders the original file list with whole-file reordering, on renders the page list. Page edits are held in the store while the mode is off, so switching back restores them. With the mode off no source document is parsed at all — the page machinery is never instantiated.

This is what the manifest is for. Download the merged PDF from the Page editing with an embedded manifest example above, then choose that single file here: the editor reads the embedded manifest, splits the document back into the pages belonging to each section, and refills Driver’s License and Certification — original file names included. From there a single section's pages can be replaced or removed without rebuilding the whole document.

Membership is resolved from the per-page tags, so a file that was reordered after export still splits correctly. A PDF with no manifest cannot be attributed to sections and is rejected with an explanation, as is one naming a section this editor does not have.

After the split, each section is editable on its own terms: Add appends another document to just that section, and Clear empties it after confirming — the other section, and its page edits, are untouched either way. The Certification section overrides the confirmation copy through clearConfirm to show that the prompt is the section's to word.

The editor's own footer Clear does one of two things, and says which in its prompt. A document the app supplied — a programmatic importMergedPdf() , or a blob bound to [source] on dbxPdfMergeEditorStore — becomes the editor's baseline, and Clear reloads it rather than discarding it. Emptying it would strand a programmatic setup in a state the app never asked for and has no easy way to detect. Use the button above to load one, edit it, then press Clear: the document comes back exactly as it arrived. Bind restoreImportOnClear: false for an editor whose Clear really should empty everything.

A file the user picked through dbx-pdf-merge-import carries no such weight — it is marked origin: 'user' and is never made the baseline. Clearing it removes the entries and the import record together, so the "Imported N section(s)" notice, any missing-section warning, and the manifest block below all go with it. With a baseline present, a user's pick sits on top of it and Clear returns to the baseline. The block below is driven by importState$ rather than the picker's imported output, so it tracks all of these paths.

The import above is bound to nothing at all. Each dbx-pdf-merge-editor-file-upload registers its slotId with the shared store, so dbx-pdf-merge-import reads the sections it accepts straight off the slots beside it — bind expectedSlotIds only to override that. Since the component exists to split a document back into slots, it renders nothing at all when no slots are declared. A file that fills only some of the expected sections still imports, with a warning naming the ones it left empty.
